# 3D

Teleplot displays 3D telemetries, **shapes**, **points** and **cameras**, in two views: a 3D view, and an image view that draws them over the pictures of a camera. Everything about them is in the library ([`packages/teleplot-js`](../packages/teleplot-js/)): the parsers, the datastore and the views `TELEPLOT.view.ViewScene3D` ([`src/113-viewScene3D.js`](../packages/teleplot-js/src/113-viewScene3D.js)) and `TELEPLOT.view.ViewImage` ([`src/114-viewImage.js`](../packages/teleplot-js/src/114-viewImage.js), built on the first one). The webapp only offers the views ("3D" and "Image" in the "+" menu of the edit mode, see [`doc/dashboard-editing.md`](dashboard-editing.md)).

## Frame

Right-handed, **x forward, y left, z up**. Angles are in radians. Units are yours (meters, millimeters...): the camera, the grid and the axes adapt to the size of what is drawn. In the view the grid is the ground (z = 0) and the axes at the origin are x red, y green, z blue.

**2D and frames**: flat shapes (rect, circle, line, polygon, arrow, text), the `2D|` lines, the 2D view, and frames (positions relative to another telemetry, or to the pixels of a picture) are described in [`2d.md`](2d.md). They are the same telemetries: flat ones lie on the ground of the 3D view, and every pose below can be given in the frame of another telemetry (`F:name`).

## Shapes

A shape is a telemetry. It has:

| What | Binary protocol | Text protocol (`3D|name:...`) | Default |
|---|---|---|---|
| kind: cube, sphere, cylinder, STL file (with its url) | attribute `TELEM_ATTR_SHAPE` | `S:cube`, `S:stl:U:"http://..."` | cube |
| position of its center | `TELEM_DATA_SHAPE_3D_POSITION` x, y, z | `P:x:y:z` | 0, 0, 0 |
| orientation | `TELEM_DATA_SHAPE_3D_QUATERNION` w, x, y, z, or `TELEM_DATA_SHAPE_3D_ROTATION` roll, pitch, yaw | `Q:x:y:z:w` or `R:roll:pitch:yaw` | not rotated |
| size along x, y, z | `TELEM_DATA_SHAPE_SIZE` | `SC:x:y:z` (`SC:x:y` keeps z, `SC:s` every axis), `RA` (radius); V1: `W` (x), `D` (y), `H` (z) | 1, 1, 1 |
| color | `TELEM_DATA_SHAPE_COLOR_STR` or `TELEM_DATA_SHAPE_COLOR_RGB` | `C:red`, `C:#2ecc71` | color of the telemetry |
| opacity | `TELEM_DATA_SHAPE_OPACITY` 0 to 255 | `O:0.5` (0 to 1) | opaque |
| texture: an image url, or the name of an image telemetry | `TELEM_DATA_SHAPE_TEXTURE` | `T:url:"http://..."`, `T:telem:camera` | none |

- Each of these is stored on its own, with its own timestamps (like any telemetry data): send what changes when it changes. Both protocols fill the same data, so a shape can even be created with one and moved with the other.
- When a shape received both rotations and quaternions, or both forms of color, the latest one is used.
- Rotations (roll, pitch, yaw) are applied in that order around the fixed x, y, z axes.
- A cylinder stands along z. The size of a sphere is its diameter (`RA:0.5` gives a size of 1). An STL file is scaled by the size.
- A texture is multiplied by the color: use white to see the image as it is. A texture taken from an image telemetry follows it (a camera stream on a screen...).
- STL files and texture urls are fetched by the browser: they must be reachable from it (same server, or with CORS headers). A file that cannot be loaded is not drawn, and the view says so in a note at its bottom, with why (`ViewScene3D.loadNote`; the 2D and image views too). A page opened from a file (`file://`) cannot read them at all: browsers refuse a request for a file of the disk, and refuse to give WebGL a picture of the disk (`ViewScene3D.isTainted`, tested when the picture is loaded), so the note says to open Teleplot from a server. Pictures do show in a 2D view (a plain canvas may draw them).

The text line is described in [`textProtocol.md`](textProtocol.md) ("3D shapes"). Differences with Teleplot V1, whose lines are all still accepted:

- the frame is z up for everything: `H` (height) is the size along z and `D` (depth) along y;
- `RA` is a real radius (V1 drew spheres half that size);
- defaults are a size of 1 and the color of the telemetry (V1: 5, purple);
- `PR` (precision) is ignored, shapes are always smooth;
- the widget label (`name,label`) is kept as the view label of the telemetry: shapes with the same label share a 3D view of the automatic dashboard, shapes without label all share one;
- everything can change at any time, including the kind of shape and its color.

## Points

A telemetry of 3D numbers (`TELEM_DATA_NUMBER_3D` in binary, the `xyz` flag in text: `drone:1.5:0.2:3|xyz`) is a point: a dot of a fixed size on screen and a line through its latest positions (option `trailLength`, 200 by default, 0 for none).

## Point clouds

A point cloud telemetry (lidar scan, depth camera...) has whole clouds as samples: every point of a cloud shares its timestamp. It is one type for 2D and 3D: a flat scan sets z to 0.

- **Points** are Cartesian, in the frame of the sensor (x forward, y left, z up). Each can carry an intensity, a color (r, g, b), or both.
- **Text**: `name:x:y:z;x:y:z;...|pc`. A field alone at the start is the timestamp of the cloud in ms (`name:1627551892437;x:y:z;...|pc`). Points have 3 values, 4 (`x:y:z:intensity`), 6 (`x:y:z:r:g:b`, 0 to 255) or 7 (`x:y:z:intensity:r:g:b`), the same number for every point of the line. `§unit`, `name,label` and the `np` / `clr` flags work as for other lines.
- **Binary**: section `TELEM_DATA_POINT_CLOUD` (35), in several parts when a cloud does not fit in a packet: see [`doc/binaryProtocol.md`](binaryProtocol.md).
- **Pose of the sensor**: sent like the one of a shape, on the same telemetry (`3D|name:P:x:y:z:R:roll:pitch:yaw`, or `Q:`; sections 25 to 27 in binary). A cloud is drawn with the pose in effect at its timestamp (the last one at or before it, nothing is interpolated), so a scan lands where the robot was.
- **Drawing**: points of a fixed size on screen (option `pointSize`, 3 px). They take their own colors when they have some, otherwise a color from their intensity (from the lowest to the highest of the cloud: blue, cyan, green, yellow, red), otherwise the color of the telemetry. `pointColorByHeight` colors them by their z instead. The legend tells how many points the cloud on display has.
- **Accumulation**: `cloudCount` (1 by default) draws that many clouds together, the current one and the ones before it, and `cloudInterval` (seconds, 0 by default) is the minimum time between two of them. Each cloud stays the one that was received, at the pose of its own time; nothing is merged. A moving 2D lidar then draws its surroundings.
- **Over images**: like every 3D telemetry, a cloud added to an image view is drawn over the picture through its camera.
- **Memory**: clouds are stored as received (`Float32Array` positions and intensities, `Uint8Array` colors, given to the renderer without a copy) and count in the memory limit; when it is reached the oldest clouds are thinned out (one of four kept), never altered.

## Cameras

A telemetry with camera intrinsics is a camera; it is usually an image telemetry, so that the 3D telemetries can be drawn over its pictures (image view, below).

| What | Binary protocol | Text protocol (`3D|name:...`, sent to the name of the image telemetry) | Default |
|---|---|---|---|
| intrinsics | `TELEM_DATA_CAMERA_INTRINSICS` width, height, fx, fy, cx, cy | `K:fx:fy:cx:cy:width:height` | none: not a camera |
| lens distortion | `TELEM_DATA_CAMERA_DISTORTION` k1, k2, p1, p2, k3 | `DC:k1:k2:p1:p2:k3` | none: plain pinhole |
| where it is | the shape position and quaternion (or rotation) sections | `P:x:y:z`, `Q:x:y:z:w` or `R:roll:pitch:yaw` | at the origin, looking along x |
| how far it is drawn in 3D views | `TELEM_DATA_SHAPE_SIZE` x | `SC` (its x; V1: `W`) | 1 |

Two conventions meet here, on purpose:

- **Intrinsics and distortion** follow the usual image convention (OpenCV, ROS `CameraInfo`): pinhole model in pixels, pixel (0, 0) is the center of the top left pixel, u to the right, v down; Brown-Conrady distortion (formulas in [`doc/binaryProtocol.md`](binaryProtocol.md)). A calibration tool gives these numbers as they are.
- **The pose** is in the frame of the scene, like any shape: the camera looks along its **x**, **y** is to the left of the image, **z** to its top. A camera that is not rotated looks along the x of the world, upright. (This is not the "optical frame" of computer vision, where z is forward: no conversion to do when the camera is mounted on a robot that already has a pose.)

The width and height of the intrinsics are the size of the image they were measured for. Pictures can be sent in another size with the same proportions: only the proportions matter to place things on them.

In a 3D view a camera is drawn as the pyramid of what it sees (without distortion), from where it is to the corners of its image.

A camera whose pictures are **depth maps** (a 16-bit gray PNG or plain numbers, `RAW|`: see [`depth.md`](depth.md)) also has its pixels drawn as points: each one along its ray, at its distance along the axis of the camera, where the camera was when the picture was taken. The 2D view draws them from above. Option `depthPoints` (250 000 by default) caps how many pixels are placed.

## The image view

A **view label** shared by an image telemetry and 3D telemetries (`PNG|camera,scene:...` and `3D|box,scene:...`) ties them together in the automatic dashboard: the 3D view of the label shows the camera, and the image view of the camera draws the shapes, points and clouds of the label over its pictures. The order in which they arrive does not matter.

`new TELEPLOT.view.ViewImage(divId, telemetries, group)`, or `TELEPLOT.view.createView("image", telemetries, group)`; it is what `TELEPLOT.view.suggestViewType()` answers for image telemetries. The first telemetry of the view that has images is the picture; the other telemetries (shapes, 3D points, other cameras) are drawn over it, as its camera saw them. Drop a shape on an image view to add it.

- **The picture is shown as received**: fitted in the view, never undistorted or otherwise modified.
- **Nothing is interpolated**: each picture is shown with the camera parameters, the camera pose and the 3D telemetries as they were when it was taken, that is the last sample of each at or before the timestamp of the image. Send the pose with (or just before) the image it goes with. The view follows the cursor of its group like the others: hover a chart to see the picture of that moment.
- **Without distortion** the scene is drawn straight by a camera built from the intrinsics. **With distortion** it is first drawn by the ideal (pinhole) camera on a wider field, the part of the ideal image that the lens brings into the picture (`ViewImage.idealWindow`), and that drawing is then bent onto the picture: for each pixel, a shader looks for the ideal point the lens sends there (the successive approximations of OpenCV's `undistortPoints`). **Without intrinsics** nothing can be placed: the picture is shown alone, with a note when the view was asked to draw something over it.
- **Legend**: the same as the 3D view (click to hide, hover to make stand out). **Options**: `outline` (only the outlines of the objects are drawn, see below; on by default, turn it off to draw the objects whole), `outlineWidth` (width of those lines in pixels of the page, 3 by default), `overlayOpacity` (percent, how much the drawing hides the picture, 70 by default), `displayLegend`, `displayNumberDecimals`, `trailLength`, `title`.
- **Outlines** (`outline` option, on by default): instead of the objects, a line in the color of each object where it ends or meets an object of another color, so the picture stays visible inside them. The objects are drawn in their plain color (no shading) and a second pass keeps the pixels around which the color changes; it is the same pass that bends the drawing when the lens has distortion, so both work together. Two objects of the same color that overlap share one outline, and a textured object also gets lines where its texture changes color.
- The WebGL canvas only exists when there is something to draw: a view that shows a picture alone costs no WebGL context.
- **Depth maps** (pictures of values, [`depth.md`](depth.md)) are drawn in colors (options `colormap`, `valueRange`, `displayColorScale`), one color per pixel; the pointer reads the value of a pixel.

`ViewImage.projectPoint(camera, point)` is the whole camera model for one point (pose aside), distortion included; `test.html` uses it to draw the pictures of its demo, over which the view must draw the same shapes at the same place.

## The 3D view

`new TELEPLOT.view.ViewScene3D(divId, telemetries, group)`, or `TELEPLOT.view.createView("3d", telemetries, group)`. `TELEPLOT.view.suggestViewType()` answers `"3d"` for shapes, 3D points and point clouds, and the automatic dashboard puts them all in one scene.

- **Camera**: until you touch it, the camera keeps everything that was drawn so far in the frame, and the origin with it (`ViewScene3D.frameExtent()`): the grid and the axes are there, and a point above the ground would otherwise be a dot in an empty view. The origin is left out when the content is tiny compared to how far away it is (more than 1000 times its size: positions on a map), where framing both would reduce it to nothing. Otherwise it only ever steps back, so a robot that moves around ends up with a steady view of its whole space. Drag to orbit, right drag (or two fingers) to pan, wheel to zoom. Double click frames what is drawn now and lets the camera follow again.
- **Time**: like the other views, a 3D view follows the cursor of its group. Hover a chart: the scene shows the shapes as they were at that time, and the trails end there. When the group is zoomed on a time range, trails do not go back before it.
- **Legend**: the same as the charts (same markup, style and folding rule, `ViewChart.fitLegend`): a row at the top with the name and the position of each telemetry; what does not fit is folded behind a "+N" chip that opens the whole list. Click an entry to hide or show its shape, hover it to fade the others.
- **Options**: `displayGrid`, `displayAxes`, `displayLegend`, `displayNumberDecimals` (positions of the legend), `trailLength`, the point cloud options (`pointSize`, `pointColorByHeight`, `cloudCount`, `cloudInterval`, `depthPoints`), and `title` like every view.
- **Look**: the scene is drawn on the card of the view, so it follows the theme (light/dark) and the appearance chosen by the layout.

## Implementation notes

- three.js is embedded in the library as `TELEPLOT.THREE` ([`src/004-lib-three.js`](../packages/teleplot-js/src/004-lib-three.js), r186, with the addons OrbitControls and STLLoader). It only ships ES modules: [`tools/embed-three.js`](../packages/teleplot-js/tools/embed-three.js) converts them (see its header to upgrade).
- What the views draw is first computed without three.js (`ViewScene3D.shapeState()`, `cameraState()`, `trailRange()`, `imageAt()`, and the camera model of `ViewImage`: `projectPoint()`, `distortPoint()`, `undistortPoint()`, `idealWindow()`, `projectionMatrix()`): that part is unit tested ([`tests/viewScene3D.test.js`](../packages/teleplot-js/tests/viewScene3D.test.js), [`tests/viewImage.test.js`](../packages/teleplot-js/tests/viewImage.test.js)). Drawing needs a browser: `test.html` has a scene for every feature.
- A view only draws when something changed (data, cursor, options, theme, camera), not on every update.
- The three.js objects of a view are kept out of any UI framework reactivity (`markRaw`): an application that wraps the library in a reactive object would otherwise break them.
- All the 3D and image views share one WebGL context (`ViewScene3D.__acquireRenderer()`): browsers only allow a limited number of them per page (about 16, the oldest is lost beyond), and a page can have more views than that. A view is drawn in a corner of the shared canvas, which is as large as the largest view, then copied to its own 2D canvas (`__present`). The context is released when the last view is disposed.
