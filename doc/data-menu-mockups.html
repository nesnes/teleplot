Data menu: window, clearing, memory

Where things stand

The popup of the pause / rate button is empty today. The library keeps 15 seconds of data per telemetry (TP.state.dataTimeout; a telemetry can ask for its own duration), counted back from its own latest sample, and nothing in the interface changes it. Nothing watches memory: with a long window, images or fast telemetries, the page grows until the browser kills it.

Protecting the page: six ways, and how they fit the rule "display telemetry, never invent any"

Every option below only ever removes stored samples. None of them creates, averages or interpolates one. They differ in what they remove and in how visible that is.

  • A. A time windowPresets and a free value for how long data is kept. What exists today, made reachable.no reduction of detail Does not bound memory by itself: one minute of images can be more than an hour of numbers.
  • B. A memory limit that forgets the oldest dataThe data is measured; over the limit, the oldest samples of the heaviest telemetries go first (their window gets shorter).no reduction of detail What is left is exactly what was received. History gets shorter than asked, and the menu must say so.
  • C. Thinning the oldest dataBeyond the recent part, keep only the lowest and highest sample of each time slice (the charts already draw this way). Text and images: keep one per slice.stored data is reduced Every sample kept is a real one, but samples are deleted for good: today's rule "stored data is never reduced" would change. Charts must mark the thinned part.
  • D. Limits per kind of dataKeep the last N images, the last N lines of text, whatever the window.no reduction of detail Images are the usual cause of a full memory: cheap and effective, but one more rule to explain.
  • E. Pause at the limitStop taking new data and say so, like the pause button.nothing removed The safest for what is stored, the worst for a live display: it freezes.
  • F. Store the data more compactlyTyped arrays for numbers (half the memory or less), images as binary instead of base64.not a setting Pushes every limit further without any trade-off; a refactoring of the datastore, independent of the menu.

Measuring memory. Browsers do not give a reliable number (the one Chrome has is not in Firefox or Safari). Teleplot can count its own data instead: samples × their size, the length of texts and images. It is an estimate, but it works everywhere and it tells which telemetry is heavy, which the browser's number cannot.

Clearing

  • Clear all dataEmpties every telemetry. Telemetries, dashboards and views stay and fill again.
  • Clear what is off screenOnly the telemetries that no view of the current dashboard displays.
  • Forget everythingData and telemetries: a fresh session, dashboards kept. Destructive: confirmed in place.
  • To decideWhether clearing while paused should be allowed (it empties a frozen display), and whether "Clear" deserves a keyboard shortcut.

2Three sections: window, memory, clear recommended

One section per question. The window has presets and a free value. Memory shows the use against the limit and lets you choose, in plain words, what Teleplot does when the limit is reached. Clear offers three scopes: the data, the data no dashboard shows, or everything including the telemetries.

Good for
Everything asked for, visible at once, each choice explained where it is made.
Watch out
A tall popup (it must scroll on small screens). "Forget everything" is destructive: it needs a confirmation in place, like deleting a dashboard.

3The history as a band

The history drawn as it is stored: every sample for the recent part, a thinned part behind it, nothing beyond. Two durations set the two edges; the memory bar reacts as they change.

Good for
Long sessions: an hour of context for the cost of a few minutes, and a picture that explains thinning better than words.
Watch out
Thinning is always on in this design: it has to be accepted as the normal behaviour, and charts must show where it starts.
Effort
High (tiered storage in the datastore, a mark in the charts).

4Short menu, details on demand, and the warning state recommended warning

Day to day the menu is as short as design 1. When memory gets close to the limit the button itself turns amber and says so, and the menu opens on what is happening, which telemetries are responsible, and the two actions that fix it. The limit and the policy sit behind "Memory settings".

Good for
Telling the user before the page is in trouble, and naming the cause: it is almost always images or a very fast telemetry.
Watch out
Settings in a second level are less discoverable. The per-telemetry sizes are estimates.
Effort
Medium. Works well combined with design 2 (same sections, plus this warning state).

Recommendation

Menu 2, with the warning state of 4. Behind it: the window (A) and a memory limit that forgets the oldest data first (B) as the default, because it never touches the detail of what is kept; limits for images (D) since they are the usual cause; thinning (C) as an explicit choice, off by default, because it changes the rule that stored data is never reduced. Compact storage (F) is worth doing on its own. Defaults to settle: the window (15 s today, 1 min suggested) and the limit (500 MB suggested).
