The Help panel is now a column of 15 accordion steps, each with an intro, several examples and notes: everything is there, but it reads as a manual and nothing says where to start or what comes next. Ten directions, from small changes to the panel to new places for the help. Every one shows, for each feature, the three things a user needs:

  • ➊ What to sendThe line, colored (name, value, flags), copyable, sendable from the page; in the language the user sends with.
  • ➋ What it looks likeA picture of the view it gives, before it is sent: people choose by the result.
  • ➌ How it worksOne or two sentences, never more on screen at once; details on demand.
  • ProgressiveBasics first; the next thing is suggested by what the user already sends; advanced features are found, not imposed.
  • RoomOne idea per screen (or card), generous spacing, a short line length, big previews, no walls of text.
  • Know where I amProgress that is real: a lesson is done when the page has received such data, not when it was read.

1A learning path

same dockprogressivereal progress

The 15 steps become 4 tracks of 3 to 5 short lessons: Basics (number, label, time, text), Over time (ranges and thresholds, timelines, stacks), In space (positions, 2D, 3D, frames, clouds, images), Organize and control (dashboards, commands).

  • The list shows only titles and checks. One lesson open at a time, as a card: Send / You will see / How it works.
  • A lesson is checked when the page receives such data (a number, a label, an ATTR| line...), from a device or from its Send button.
  • The next lesson is highlighted; tracks after Basics are folded with a one-line promise ("Draw your robot on a map").

Cost: lessons must be rewritten short. Risk: a path feels linear to an expert (search and "jump to" help).

2A wider guide with a live split

wide dock, 2 columnsresult first

When Help is open it takes about 40 % of the width. Left: the message and its explanation. Right: a real view of the library showing the example, live, as it would look on the dashboard. A stepper (‹ 3 of 15 ›) walks through the steps; the line under the preview says what changed.

  • Editing the line updates the preview as you type (the parser already exists: helpDescribe).
  • "Add to my dashboard" puts the previewed view on the current dashboard.

Cost: a preview datastore separate from the real one. Risk: the dashboard shrinks while Help is open (it can be a modal instead).

3"What do you want to see?" gallery

same dockoutcome firstscannable

Start from the result, not from the syntax: a grid of thumbnails (a curve, a gauge with limits, a timeline, a map, a 3D scene, a camera, a dashboard, controls). A click opens a sheet: the picture large, the line to send, how it works, and "Related" (the gauge leads to thresholds, the map to frames).

  • Thumbnails that the user has already produced get a check: the gallery doubles as a map of what is left to discover.
  • Nothing about the syntax until a result is chosen: newcomers recognize what they want.

Risk: features with no strong picture (time, labels) need a home: the sheet of the curve covers them.

4Help in context: the next step, where it matters

no panel neededprogressive by usagemust stay quiet

The help comes to the data. The empty dashboard explains the first message. When a kind of telemetry shows up, a small card offers one next step for it ("battery is a number: give it a range to get a gauge"), with the line to send. The Help panel lists these suggestions, plus everything else.

  • One suggestion at a time, dismissable ("Not now", "Never for this"), never while the user is dragging or editing.
  • Suggestions follow what is sent: text → timeline; 3 numbers → 3D; an image → its camera; anything → commands, once.

Risk: becomes noise if overdone: a budget of one card per minute at most, off with one click.

5A playground with small challenges

full screen, on demandlearning by doingengaging

"Open the playground" (from Help or the welcome screen): an editor of lines on the left, a small live dashboard on the right, and a goal on top: "Make the battery turn amber below 22 V". The user types; the playground checks the result (a threshold named low is set) and gives the next challenge. Hints come in two levels: a nudge, then the line.

  • Nothing touches the real data: a separate datastore, thrown away (or "Send all of it to my dashboard").
  • 12 challenges, one per feature, each under a minute.

Cost: the largest to build. Best for workshops and first contact; experts never need to open it.

6The anatomy of a message

same dockone mental modelfor experts too

Every text message has the same shape. The top of the panel draws it once, big: name,label:time:value§unit|flags, each part in its color with a callout. Each part is clickable: the label opens "shown together", the flags open a list of flags (chips), each with a one-line effect and a mini preview. Line families that start with a prefix (ATTR|, TH|, 3D|, 2D|, DASH|, ACK|) are a second row of chips.

Strength: a single picture explains 80 % of the protocol. Weakness: abstract for someone who wants "a chart, now" (pair it with 1 or 3).

7Ask: "how do I…"

same dockfast for a goalneeds good wording

A search box first, phrased as a question, with suggestions under it ("draw a robot on a map", "change a value from the page", "see when a task runs"). Answers are the same lesson cards (send / see / how), matched on words and synonyms from a local index (no network, no AI). Below the box, the five most common questions; "Browse everything" opens the full list.

Strength: users arrive with a goal. Weakness: an empty box teaches nothing: the suggestions matter.

8Tours of the robot sample

over the dashboardlearning from a real example

The robot sample already uses every feature. A tour lights up its views one by one, and for each one shows the line the robot sends to get it ("This band is robot.state: it sends robot.state:turning|t"). Tours by theme: "The basics" (4 stops), "Time" (3), "Space" (5), "Control" (3). At the end of each stop: "Try it with your device" copies the line.

Strength: the most engaging, real data, nothing to type. Weakness: depends on the sample dashboard staying in shape.

9Your stack first: full programs, not lines

same dockcopy, run, see

The first question is "What sends your data?" (Terminal, Python, C++, Arduino, ESP32, Node...), remembered. Then every lesson is a complete, runnable program in that language (the setup included), 5 to 15 lines, with what to expect next to it. The text protocol line stays one click away ("The line it sends").

  • Five essentials up front (a number, text, a position, a gauge, a command); the rest under "More with Python".
  • Python and C++ use the client libraries (teleplot.py, Teleplot.h), so commands are 3 lines.

Cost: snippets per language must be kept tested (the Help tests already parse every line).

10A feature catalog with levels and "new"

same dock or a pagediscover what existsrelease notes

Cards grouped by family (Numbers, Text, Space, Images, Dashboards, Control), each with a level (● basic, ●● more, ●●● advanced) and a small picture. Filters by level and by family; a New badge for what came with the last versions (commands, joystick, timelines), so returning users see what changed. A card opens the same three parts as elsewhere.

Strength: a complete map, good for returning users. Weakness: a catalog does not tell a newcomer where to start (filters default to ●).

How they compare, and a combination
