Sources panel: design proposals

What the panel is for

One question: is my data arriving, and if not, where does it stop? Today the panel lists each connection's type and address, with a red cross when it is down. Every mock-up below shows the same situation, so they can be compared: a local server that works (UDP and one serial port, two binary clients), and a second server that cannot be reached.

  • 1. Connection stateEach Teleplot server: address, connected / reconnecting / never reached, retry now. Add, edit, remove.
  • 2. InputsUDP (port, protocols seen, age of the last packet) and serial ports (port, baud rate, connect, send).
  • 3. Flow per sourceSamples per second and time since the last data: "connected but silent" must be visible.
  • 4. ClientsBinary-protocol clients: name, id, number of telemetries, last seen.
  • 5. ProblemsInvalid packets and lines that could not be read, counted per source (today: only in the browser console).
  • 6. GuidanceWhen nothing arrives: which step fails and what to try, with a link to the Help examples.
  • 7. Data controlsHow long data is kept, clear all data, the paused state.
  • 8. Sample dataThe robot sample as a source with start / stop (today in the Help panel).
  • To decide: serialThe library has a serial input but the V2 server does not implement it. Server work, or the browser's Web Serial API (no server, Chromium only).
  • To decide: remote commandsThe V1 "telecmd" calls: under each source here, or in a panel of their own.

Ten designs

Each one is drawn at the real width of the left dock, with the webapp's surfaces, colors and type. They are static pictures.

1Status cards recommended base

One card per source, colored by its state like the telemetry tiles. The collapsed card says the three things that matter (state, rate, age of the last data); expanded, it lists its inputs, clients and problems, and holds its actions.

Good for
Everyone: readable at a glance, same visual language as the Telemetries panel, room to grow (a new kind of source is a new card).
Watch out
Inputs and clients are a list inside a card: with many of them the card gets long.
Effort
Low. Needs per-source rate and error counters in the library.

2Tree of the data path

Server, then its inputs, then the clients seen on each input, folded like the groups of the Telemetries panel. A problem low in the tree colors its parents.

Good for
Setups with several devices: it shows exactly which client on which input went silent.
Watch out
Three levels of indentation in a narrow panel; a newcomer with one source sees structure they do not need.
Effort
Medium. The library must remember which input each client and telemetry came from.

3Pipeline diagram

The chain from the device to the page, drawn as it is, with a state at each hop and on each link. When data stops, the broken link is the dashed red one.

Good for
Understanding and troubleshooting: it teaches how Teleplot works while showing where it fails.
Watch out
One chain per source: with several sources it needs tabs or a lot of height. The first hop is partly a guess (the page cannot see a device that sends nothing).
Effort
Medium.

4Health summary first recommended top

The answer before the details: one block that says whether data is flowing, how much, since when, and whether anything is wrong. The sources and the data controls come under it.

Good for
The moment you open the panel because something looks off. It also gives the data controls (retention, clear) a natural home.
Watch out
The summary repeats the rate of the top menu; it must add something (the history, the problems) to earn its place.
Effort
Low to medium (a short history of the rate).

5Troubleshooting checklist recommended when it fails

For a source that sends nothing, the panel runs the checks in the order of the data path and stops at the first one that fails, with what to try. Sources that work stay as one-line cards.

Good for
Newcomers, and the first minutes with a new device: "nothing shows up" is the most common question, and this answers it without the documentation.
Watch out
Advice the page cannot verify (firewalls, the device's own code) must be phrased as things to check, not as facts.
Effort
Medium: the checks are simple, writing good hints takes care.

6Tabs by kind

Network, Serial, Clients and Sample each get a tab with exactly the controls of that kind (a form to connect, a port list, a client list).

Good for
Keeping each screen simple when the panel has a lot to offer, serial settings in particular.
Watch out
The overall state is spread over tabs: a failing serial port is invisible from the Network tab unless the tabs carry status marks.
Effort
Low.

7Add a source first

Large tiles for what can be added, each opening a short form; the sources that exist are compact chips under them.

Good for
The first run, and discovering that serial or the sample exist at all.
Watch out
After the first minute the tiles take the best place for something rarely used, and the chips are too small to say much about a source in trouble.
Effort
Low. Works well as the empty state of another design.

8Dense table

One row per server, input and client, with the same columns for all: state, rate, age of the last data, errors. Rows open for their settings.

Good for
Experts with many devices: the most information per line, easy to scan down a column.
Watch out
It already fills the width of the dock with six columns, and gives a newcomer numbers without telling what to do about them.
Effort
Low to medium.

9Cards with a live console recommended later

Each source can show the last lines and packets it received, as they came, with the ones that could not be read in red and the reason. Serial ports and command channels get a box to send text.

Good for
Debugging a device's output: "my line is ignored" becomes visible, with why. It is also where a serial terminal naturally lives.
Watch out
At high rates it must sample what it shows, or it costs more than the charts. It shows received data as it is: no reformatting.
Effort
High. The library has to keep the last raw messages per input, and the parsers to report why a line was refused.

10Activity timeline

Every source, input or client is a row with its rate over the last minute. Gaps, drop-outs and the moment something went silent are visible without watching the panel all the time.

Good for
Unreliable links (radio, long serial cables): "it drops every 30 seconds" shows at once.
Watch out
It shows when, not why: it needs the hints of another design next to it. The curves are measured rates, drawn as they were, not smoothed.
Effort
Medium (a per-source history of the rate).

Recommendation

Combine three of them. 4 at the top: one block that says whether data flows, with the data controls. 1 as the body: a card per source that opens on its inputs, clients, problems and actions. 5 for any source that sends nothing: the checks, and what to try. 7's tiles make a good empty state when no source exists yet, and 9's console is the most valuable later addition for experts, inside the opened card.
