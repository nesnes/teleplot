# Teleplot V2 — project memory

Rework of Teleplot for better performance and UI.

## Guidelines
- Teleplot displays telemetry, it never invents any: no interpolation between samples (use the last sample at or before the time shown), and incoming data is never modified (ex: images are not undistorted; adapt what is drawn instead). Removing old samples to bound memory is allowed (data window, memory limit); creating or averaging samples is not.
- Minimize dependencies; always tell the user when wanting to add one.
- Goals: performance of data ingestion and display; UI intuitive for newcomers yet powerful for experts; retro-compatible with the V1 text-based protocol.
- For each new feature, decide whether it belongs in the lib (`packages/teleplot-js`) or in the GUI (`packages/webapp`).
- `packages/teleplot-js/`: everything about telemetry and how it is displayed. Split into `src/` files aggregated by `build.sh` (libs included). Keep `test.html` updated with a demo of ALL lib features: it is a page of sections (side index) made of cards; add a feature with `demo(title, what to look for, [width, height], (id) => {...})` in its section (the card shows the view and the code of that function), and the code that sends its telemetries with `data(title, note, () => {...})`.
- `packages/webapp/`: GUI for end users, exposes all lib features.
- `clients/`: source libraries per language, as simple as possible.
- `doc/`: documentation, must be expanded and kept updated.
- `README.md`: V1 info + V2 targets at the end; must be rewritten and kept updated.
- Legacy V1 (reference only, do NOT update): `server/`, `vscode/`, `images/`, other old folders.
- Note: the folder is `packages/` (plural), not `package/`.

## Build
- `cd packages/teleplot-js && ./build.sh` concatenates `src/NNN-*.js` by numeric prefix into `teleplot-js.js`, then copies it to `packages/webapp/libs/`. Always rebuild after editing `src/`.
- Everything lives inside one function `initTeleplot(TELEPLOT)` opened in `000-init.js` and closed in `999-export.js`. Vue (003), uPlot (001/002) and three.js (004, `TELEPLOT.THREE`, generated by `tools/embed-three.js`: do not edit by hand) are embedded.

- CI and releases: `.github/workflows/teleplot-v2.yml` builds, runs both test suites and packages `teleplot-js.js`, `teleplot-webapp.zip`, `teleplot-server.zip` (server + webapp as `www/`) and one executable per platform (`npm run make` in `packages/server`: `@yao-pkg/pkg` through npx, built on macOS so the Apple silicon one is signed). A tag `v2*` publishes them as a GitHub release. Shell scripts and workflows are LF, not CRLF.

## Protocol
- Binary: little-endian everywhere (C++ `BinaryEncoder` default, JS `_parseDataBinary_LITTLE_ENDIAN`), marker 0x10, version 1, client id uint16, typed sections (client name, telem attr, data number/2D/3D/text/image, 3D shape position/rotation/quaternion/color/opacity/size/texture, camera intrinsics/distortion), checksum still TODO. Spec in `doc/binaryProtocol.md`; constants in `src/011-protocol.js`.
- View label: `name,label` in text, `TELEM_ATTR_VIEW_LABEL` in binary. Telemetries with the same label share a view (per kind of view, titled with the label) in the auto dashboard; the webapp's Telemetries panel has a card per label to drag them together. It only decides the first placement. Views can follow labels (`options.followLabels`, `view.followLabel(label)`): new telemetries of a followed label that the view can display (`suitsTelemetry`) are added to it; the auto dashboard's label views and the views a label card is dropped on (drag type `text/x-teleplot-drag-label`) follow it. A label also ties a camera to its scene: a 3D view takes the image telemetries of its label (its cameras), and in the auto dashboard the image view of a labelled image telemetry follows the label too (shapes, points and clouds of the label are drawn over the picture), whichever comes first.
- Point clouds (lidar scans...): data type `TELEM_DATA_POINT_CLOUD` (35), one sample = one whole cloud, stored as typed arrays in 3 channels (positions `Float32Array` x,y,z..., intensities `Float32Array` or null, colors `Uint8Array` r,g,b... or null). Cartesian, in the sensor frame (2D scan: z = 0); the sensor pose is sent as shape position / rotation on the same telemetry. Text: `name:x:y:z;x:y:z|pc` (a field alone = timestamp; 4, 6 or 7 values per point add intensity and / or rgb). Binary: multi-part like images. Drawn by `ViewScene3D` (kind "cloud", `__updateCloud`, options `pointSize`, `pointColorByHeight`, `cloudCount` / `cloudInterval` for accumulation) and so by `ViewImage` overlays. See `doc/3d.md` "Point clouds".
- Text: V1 `name:value` style, UDP port 47269; commands UDP 47268. Commands from the page (telecmd): see "Commands". `DASH|` lines describe dashboards (see "Dashboards as text"), `ATTR|` lines attributes (the range) and `TH|` lines thresholds (see "States over time, ranges and thresholds"). Flags `xy`, `xyz` (3D point), `pc` (point cloud), `t` (text as a state), `log` (text as a log: attribute `TELEM_ATTR_LOG` 7, also set by `>` lines), `np`, `clr`. State or log is the same text data and both views display both; it only changes `suggestViewType` ("values" or "log"), so the default view, and in the auto dashboard logs without a label share one log view. `3D|name:props` lines describe shapes (and, with `K`/`DC`, the camera of an image telemetry): each property is stored in the data type (or attribute) the binary protocol has for it, so both protocols give the same telemetry.

## States over time, ranges and thresholds
- Spec in `doc/time-views.md`. No new kind of text data: a timeline and the marks of a chart display text telemetries. A state (`t`) lasts until the next different text (the same text sent again continues it), an empty text is a sample ("nothing": a hole; `name:|t`), a log (`log`) is an instant. A text may hold colons: its time is a first field that is a number (a text with a colon used to be stored at a NaN time; `addData` now refuses any timestamp that is not `>= 0`).
- `116-viewTimeline.js`: `ViewTimeline` (type `teleplot-timeline`, "timeline" in `createView`, `VIEW_TYPES`, `DASH|` lines and the editor menus), a plain 2D canvas. `buildLane` (no canvas, tested) gives bands / ticks / "mixed" blocks (several states in a couple of pixels are never drawn as one of them); `getTimeWindow`: the zoom of the group, else what the numbers and texts of the views of the group cover (a state that is not resent does not make time pass), within the data window, with 4 % of room for a latest state that has no width yet; colors by order of appearance per view (`view.colors`), error / warning words take the theme colors; drag = zoom of the group, double click = `backToLive`. It is the default view of stacks only (`suggestViewType` answers "timeline" for a text telemetry with `TELEM_ATTR_STACK`; in the auto dashboard stacks without label share one timeline, like logs share a log view); for the other texts and for numbers it is asked for. Numbers can have a lane too (`getSources` gives each telemetry a kind; `suitsTelemetry` stays text only, so numbers are added on purpose): "limits" when the number has thresholds (`ViewTimeline.limitRuns(telem)`: runs of "past the same threshold", cached in a `WeakMap` per number entry and completed on append, rebuilt when the thresholds change; a band starts at the sample that passed the limit, never at an interpolated crossing), "line" otherwise (`buildLine`: real samples from a `MinMaxDecimator` per telemetry in `view.decimators` (`markRaw`), joined by straight segments, scaled on the range or on what is drawn), "values" with the option `numbers: "text"` (per view or per telemetry: `TELEPLOT.textRuns` works on a number entry too). `lane.runs` is what the pointer asks for the real extent of a band.
- Stacks: a text telemetry with `TELEM_ATTR_STACK` (10; `stack` flag in text, which is still a text flag: "the last flag used tells") is a state whose text is a path (`loop/plan/search`, separator `/` fixed). Device time: the first numeric field in text (ms, decimals), the sample timestamp in binary. `TELEPLOT.stackRuns(entry)` (107, cached like `textRuns`): `levels[d]` = runs of the path down to depth d. In the timeline (kind "stack") a lane has `rows` (one `buildLane` per level; `item.text` = the whole path, `item.label` = its last part, colored by label) and `levels` (for the pointer). Lanes now have their own `top` / `height` / `rowHeight` (`__layout`); `ViewTimeline.laneSize(depth, limit, rowHeight, ROW_MIN)`: full rows up to `stackDepth` (default 4, 0 = no limit), then thinner rows down to `ROW_MIN` (7 px; no text under 11), then the lane grows. The robot sample sends one: `robot.camera.task` (`frame/expose`, `frame/read out`, `frame/encode`, `frame/detect`, then empty, 5 times per second, dated with `performance.now()`): "read out" and "encode" are measured on the real picture code, the two others are pretended and vary.
- Chart (111): text telemetries of its list are marks (`getMarkTelemetries`, `ViewChart.buildMarks`: a log = every line, a state = where it changes to something; closer than `MARK_GAP` pixels = folded, drawn as a short tick). `chart.overlay` (`markRaw`: `{thresholds, marks}`) is built by `buildOverlay` only when its key changes and drawn in the uPlot `draw` hook (`drawOverlay`). Options `thresholds` ("fit" / "show" / "hide") and `scale` ("auto" / "range"), `getScaleRange` is the y range of uPlot. `acceptedDataTypes` (numbers + texts) is what the edit panel offers to add; `supportedDataTypes` stays "what has a series".
- Range: attribute `TELEM_ATTR_RANGE` (9) `{min, max}` (a side may be undefined), `ATTR|name|min=..|max=..` in text (a new line family: unknown keys are "not understood"), two float64 in binary. `telem.getRange()`.
- Thresholds: data type `SECTION_TYPE_TELEM_DATA_THRESHOLD` (40), 4 channels (operator `THRESHOLD_BELOW` 0 / `THRESHOLD_ABOVE` 1, value, name, color), one sample = one limit from its timestamp on; same name = replaced, NaN = removed. Text: `TH|name:[time:]low<10.5:hot>70,red` (names escape `% : ; | < > ,` as `%XX`). `telem.getThresholds(t)` (index per name on the raw entry, `__thresholdIndex`), `getThresholdStatus(value, t)` (the passed limit closest to the value), `getThresholdSteps(from, to)`.
- A telemetry that only has attributes or thresholds has nothing to display: `telem.hasContent()` is false, and the new telemetry hooks (auto dashboard, labels...) are called when its first data comes (`_datastore_announce`), not 100 ms after its creation. Code that picks "the data type" of a telemetry must skip type 40 (`suggestViewType` does).
- Kept: the data window keeps the last sample before it of a state (not of a log) and of each threshold name (`__deleteOldThresholds`); thresholds are neither thinned nor forgotten by the memory policy; a time range export also writes the thresholds in force when it starts (`_files_indexes`). Front pruning bumps `entry.pruned` (caches by index start again).
- Values (110): `ViewCurrentValue.gauge(telem, value, t)` gives the bar (range with both ends, ticks = thresholds inside it) and the status (name + color, never color alone). Under the bar, option `displayScale` writes the ends of the range and the names of the thresholds; `fitScales` (DOM, after render, when `scaleKey` or the width changes) places them and `ViewCurrentValue.fitLabels` (tested) drops the ones that overlap, thresholds first. The unit is written after the value (small, muted), not after the name; with the status chip it wraps to its own line in a narrow view (the number never breaks).
- Webapp: Help tiles "A gauge", "A timeline", "Marks on a chart" and "What runs" (`helpParts` / `helpDescribe` know `ATTR|` and `TH|`); the robot sample has ranges (battery, heading, distance), thresholds (currents, battery, and `robot.distance` "wall" that follows `bot.reach`, which changes every 30 s), `robot.zone` ("dock" or empty), a timeline row, and the state / motor log as marks on its charts.
- Description: `ATTR|name|desc=` (`TELEM_ATTR_DESC` 14), `telem.getDescription()`; `TELEPLOT.view.telemetryTip(telem)` (name, unit, description) is the tooltip of a telemetry's name in every view (chart and scene legends, values, log names, timeline gutter and tips, joystick) and in the webapp panels (Telemetries, Edit, Sources commands, Export): use it for any new place that shows a telemetry name.
- Not done: the C++ client (`clients/cpp/Teleplot.h`) has neither the range attribute nor the threshold section (it already lacks view labels, logs, frames, 2D and clouds).

## Server and webapp
- `packages/server/main.js` (Express + express-ws), spec in `doc/server.md`: relays UDP 47269 to WebSocket on 8080, forwards commands (`{cmd: text}`, not the V1 serial ones) to UDP 47268, serves `www/` or `../webapp`. Command line options for ports, hosts, `--allow-origin`, `--batch`, `--max-buffer`, `--www`, `--serve [/url=]folder` (extra folders served after the webapp, repeatable); `startServer(options)` is exported for the tests (`packages/server/test.sh`, needs `npm ci`: real servers on free ports).
- Server to page: every 50 ms one JSON text `{time, packets: [[time, text]...], dropped}` (times on a clock of the server that only counts) and one binary message (a packet alone as is, several framed like a binary file: `FILE_MAGIC` + length + packet). The lib dates untimestamped text samples when the server received their packet (`ConnectionTeleplotServer.__receivePackets`, `__serverClockOffset`: smallest "received - sent" seen = difference between the two clocks), so `parseDataText` uses `msg.timestamp` (ms) whenever it is given. Pages of other sites are refused on their `Origin` (pages of local files are origin `null`: `--allow-origin null`). A page too slow loses packets (`dropped`, `connection.stats.dropped`, shown in the Sources panel) instead of filling the memory of the server.
- Webapp: Vue 3 (`main.js`, `index.html`, `components/` panel-help/sources/telemetries/edit + dashboard.js + dashboard-editor.js, `css/style.css` + `css/editor.css`, icofont). Default connection 127.0.0.1:8080.

## Performance
- Scenes (2D / 3D views, frames, clouds): measured figures and limits in `doc/performance.md` "Scenes". Rules that came out of it: what a view reads on every update must be raw (`ViewScene2D.items` is `markRaw`); poses of frames are cached during an update (`ViewScene3D.__poseCache`, set by the hook in 998); old data is pruned 4 times per second, not on every update; a negative timestamp must never reach `getDataPoint` (it means "latest").
- Charts decimate data before giving it to uPlot (avoids `uPlot.join` on all stored points): see `doc/performance.md`. Stored data is not reduced by the display; it is only reduced when the memory limit is reached (`TP.state.memoryLimit` / `memoryPolicy`, default "thin": `telemetry.thinOldest()` keeps real samples, fewer of them, and charts mark the thinned part), see `doc/performance.md` "Memory". Chart option `decimation` (default true).
- `packages/teleplot-js/test-performance.html` = stress/perf page (text or binary protocol, configurable through URL, reports fps/ingestion/heap/update time). Keep it working when touching ingestion or views. `test.html` links to it.
- Files are CRLF (Windows checkout): keep CRLF when editing/creating files.

## Commands (telecmd)
- Spec and what was built: `doc/telecmd.md`; reference design `doc/telecmd-reference.html`. Settings are writable telemetries (`ATTR|name|write[=type]|min|max|step|choices|rate|hold|axes|desc`, binary `TELEM_ATTR_WRITE` 11, `TELEM_ATTR_CHOICES` 12): the page sends the line the device would send, the device's echo (a new sample equal to it, `entry.lastUpdate` after the send) is the acknowledgement; requests are resent every 250 ms for 2 s and end applied / kept / refused (`ACK|name:err:why`) / noanswer. Actions (`ATTR|name|action|title|confirm|longpress|color`, `ATTR|name|arg=..|type=..|optional|default=..`, binary 11 / 13 / 15) are calls with named typed arguments (`!name#id:arg=value`, section 41) answered `ACK|name#id:run`, `ok[:text]`, `err:why` (section 42); answers are log samples of the action ("#21 ok"), `TELEPLOT.commands.calls()` reads them back. Types: number, bool, text, xy, xyz, pose2d (x, y, yaw radians; stored as NUMBER_3D, the device publishes it with `|xyz`).
- `025-commands.js` (`TELEPLOT.commands`): nothing is sent while `TELEPLOT.state.commands` is false (CMD button, off at every start) nor while paused, nor to telemetries of files. Work in `__update` (998 hook). Writes go back through `telemetry.sourceId` and `telemetry.endpoint` (the sender index the server gives), in the protocol the device speaks (binary when the telemetry has a client id). What the page sends is logged as the log telemetry `commands.sent` (source "page"). Continuous settings (`rate` + `hold`): `hold()` / `release()`, rest value sent 3 times; the device stops by itself after `hold` ms.
- Views: values view edits in place when CMD is on (`commandState` computed without DOM; caret above the bar = target, no caret = nothing asked; status as icons only), actions get a button and a form; joystick view (117, one continuous setting: pad / rocker / pad + rotation rocker / one stick for `axes=x,yaw`; also displays the reported value; `keyboard` option off by default, sets `TELEPLOT.commands.keyboardCaptured`); timeline lane kind "calls" and request ticks; 2D view draws a writable pose2d as a pose and edits pose2d / xy settings with a ghost (move and turn handles, Send / Enter / Esc). CMD off: no command UI anywhere; touching a command then (joystick, value or bar of a setting, writable pose on a 2D view) sends nothing and says "Commands are off" with a Switch on button (`TELEPLOT.commands.blockedWhileOff`, `onBlockedHooks`: the webapp flashes its CMD button). A continuous setting can be refused with `ACK|name:err:why` answered to each value it cannot apply: kept 1.5 s after the last one (`TELEPLOT.commands.refusal`), shown in red under the joystick; the robot sample refuses `cmd_vel` outside manual mode.
- Server: hello `{readOnly, senders}`, `senders` / `binary` in the JSON messages, `{write | writeBinary, to}` sent back from the telemetry socket to the sender, `--read-only`. Clients: `clients/python/teleplot.py` (+ `test_teleplot.py`), `clients/cpp/Teleplot.h` (`param`, `action`, `poll`, + `test_commands.cpp`), `clients/arduino/commands`.
- The Help panel sends its messages from a pretend device (`helpDevice` in `panel-help.js`, local connection "Help panel"): it applies settings and answers calls, so the Control tiles can be tried for real.
- Webapp: CMD button (`top-menu.js`, shortcut C), pens in the Telemetries panel, commands per device in the Sources panel, Help tiles "Settings", "Buttons", "A joystick", "A pose on the map", robot sample takes commands through a local connection (`isSample`, hidden from the Sources list: it has its own card).

## Time groups
- Views of a group (`view.group`, state in `TELEPLOT.view.groups[name]`) share zoom and cursor. `view.group` is no longer set once: every view and layout has options `timeGroup` ("inherit" default / "dashboard" / "custom") and `timeGroupName`, and `TELEPLOT.view.resolveTimeGroups(root, base)` (100-views.js) gives each view of a tree its group (custom key = base + `TIME_GROUP_SEPARATOR` + name). Dashboards do it on every update (`TELEPLOT.dashboards.resolveTimeGroups`, hook in 998) with base = the dashboard name, so moving a view, renaming a dashboard or changing the option just works; groups nobody uses any more are pruned.
- `TELEPLOT.dashboards.setTimeGroup(dashboard, view, mode, name)` ("custom" without a name creates "Time N"), `getTimeGroups`, `renameTimeGroup`. Marks (tag + frame, `Views.__syncTimeGroup`, `view.timeGroupMark`) show where a group starts: always with `TELEPLOT.view.showTimeGroups` (the webapp sets it in edit mode), otherwise only while zoomed. GUI: "Time group" in `panel-edit.js`. See `doc/dashboard-editing.md` "Time groups".

## 2D drawings and frames
- Sizes: `SC:x:y:z` (scale, values like `P`: `SC:x:y` keeps z, `SC:s` every axis, empty keeps), on shapes that are 1 by default (an STL in its own units); `W`/`D`/`H` (V1, H is y in a `2D|` line) and `RA` still work; files are written with `SC`.
- An image telemetry with a place of its own (shape data, no `K`) defaults to the 2D/3D view (`suggestViewType`), so the order and timing of its picture and its `2D|` line do not matter.
- Spec in `doc/2d.md`. 2D is 3D with z = 0: `2D|` lines (040, `_parseDataText_parse3D(msg, now, flat)`) store in the same data types; no separate 2D section family. New shape types rect 3, circle 4, line 5, polygon 6, arrow 7, text 8 (`FLAT_SHAPE_TYPES`); the points of a line / polygon are point cloud samples (35); new sections vector 37, text 38, line width 39; text props `PT` (variable length), `V`, `TX`, `LW`, `TS` (= size), `F`, `FPX`.
- Widths (`LW`) and text sizes (`TS`) are in frame units like everything else; not sent = as thin as the screen draws / a steady size on screen. Views never draw a given width thinner than 1 px.
- Frames: `TELEM_ATTR_FRAME` (8) `{type, name}`. `FRAME_TYPE_POSE`: `ViewScene3D.shapeState` composes the pose with `frameOf` (recursive, max 16, parent found by `datastore.findByName`, parent pose at the time shown; trails use the parent pose at each sample time: `pointPositions`). `FRAME_TYPE_PIXELS`: only image views of that picture draw it (`__takesFrame`, `__takePixelTelemetries`, a 2D canvas over the picture, `pixelDrawings` option); scenes skip it.
- `115-viewScene2D.js`: `ViewScene2D extends ViewScene3D` (same sources, legend, options), plain 2D canvas (no WebGL), `buildItems` (no canvas, tested) + `draw` / `drawGrid`; solids drawn as the hull of what they cover. How it looks at the scene: options `axisRight` / `axisUp` ("x", "-y", "z"...; `ViewScene2D.axes()`), which also give the draw order (nearer the viewer last). An image telemetry that has shape data (a `2D|` line on its own name) and no intrinsics is a rect textured with its own pictures (`shapeState().texture.own`), in 2D and 3D views. Option schemas can have `type: "choice"` (`choices: [[value, label]]`), rendered as a select by `panel-edit.js`. The 3D view draws flat types in `__updateFlat` (kind "flat": lines / ribbons, triangulated polygons, sprites for texts) and rect / circle as flat meshes.
- Kinds: `isPoint` also takes 2D numbers (z = 0); `isShape` needs shape data, or the attribute alone when the telemetry has no positions of its own (a point given a frame stays a point); `isCloud` is false for line / polygon. `isFlat` decides the default view: `suggestViewType` returns "2d" (xy, flat shapes, clouds with z = 0), "3d", or "image" for pixel frames (the auto dashboard skips those: image views take them). 2D and 3D views `suitsTelemetry` everything of a scene.
- Webapp: view type "2d" in the editor menus; Help tiles "A map" and "Moving together"; the robot sample carries its parts in the frame of its body, has a Map (2D view) and draws a detection in the camera's pixels.

## Dashboards as text
- `151-dashboardText.js`, spec in `doc/dashboard-text.md`: one line per view addressed by its path, `DASH|Robot/top/Motion:chart:speed,accel|w=3` (type: row/column/grid/stack/chart/values/log/3d/image/none; options = layout and view option names, plus `w`, `h`, `title`, `time`, `follow`; `%XX` escaping). The same lines are the export file, a message of the text protocol (040) and the binary section `SECTION_TYPE_DASHBOARD` (2). No JSON form: one grammar.
- `exportText(name)`, `importText(text)` (always new dashboards, "Robot 2" when taken), `receiveLine/receiveText` (applied only when the line differs from the last one received for its path: user edits survive repeats; `TELEPLOT.dashboards.received`, raw), `onReceivedDashboardHooks` (the webapp shows the dashboard unless the user is on one of their own or editing). Views keep the key of their path in `view.key`.
- A view label that is a path (`speed,Robot/Motion:12.5`) places its telemetry (`placeTelemetry`, new telemetry hook): dashboard and view created, one view per kind (`Motion`, `Motion#values`), skipped by the auto dashboard.
- Views accept names of telemetries that do not exist yet; a hook in 103 swaps the name for the id when a binary telemetry with that name shows up.
- In the webapp the library is wrapped in Vue proxies: dashboards (like views) are compared by id, never `===`, and always taken from `TELEPLOT.dashboards.dashboards` (a bug of this kind passed the lib tests and only showed in the browser).
- GUI: a per-dashboard export button in the dashboard list of `top-menu.js` (`exportDashboardFile`); its "Import…" hands the file to the Export and import panel (`ctx.droppedFiles` + `ctx.exportOpen`), the only place where files are opened; Help tiles "Your dashboard" and "Choose where".

## Data files
- File extensions written by the webapp: `.teleplot` (binary), `.teleplot.txt` (text protocol lines, dashboards alone included), `.teleplot.csv`. Opening does not depend on them (content is sniffed; `.csv` only forces CSV).
- `160-files.js`, spec in `doc/files.md`: `TELEPLOT.files.exportBinary/exportText(options)` return `{parts, samples, skipped}` (parts for a Blob; options `telemetries`, `from`, `to`, `dashboards`), `importData(data, options)` / `createImport()` (`add(piece)` cut anywhere, `finish()`), `isBinary`. A file is what a device would have sent: text = lines of the text protocol (a device can log them to an SD card), binary = `FILE_MAGIC` then `{length uint32}{packet}`; importing goes through `parseDataText` / `parseDataBinary` (pause lifted meanwhile, `DASH` lines redirected to `dashboards.createImport` by `dashboards.withImport`, what was added counted by `datastore.watchAdds`).
- Binary is lossless (tests compare the whole store after a round trip): values a float32 would round go in `SECTION_TYPE_TELEM_DATA_FLOAT64` (36, generic for numeric data types), timestamps are written so that the parser reads the same double back, name-identified telemetries use the reserved client id `CLIENT_ID_NAMED` (0xFFFF). Text is what the text protocol can say: what it cannot is skipped and counted, never altered.
- Known behaviours: importing adds samples (a file imported twice is stored twice); the data window counts from the newest sample of each telemetry, so a long old file needs `extendWindow` (or a longer window).
- CSV (`exportCSV`, `previewCSV`, and opened by `createImport`): numbers, 2D/3D numbers and text only; layout columns (empty cell = no sample at that very time, never filled) or lines; separator `,` `;` tab; numbers always with a point; time iso / ms / s. `estimate(format, options)` sizes an export before writing it.
- `createImport({dryRun: true})` describes a file without storing anything (`datastore.dryRun` + `rememberIdentity`, undone after each piece because live data keeps arriving between pieces). `removeImported(result)` takes an import back by time range per telemetry (samples are not tagged with their origin).
- GUI: `webapp/components/panel-export.js` (right dock like Help and in its place, `ctx.exportOpen`, shortcut X; design studies `doc/export-panel-mockups.html` and `-2.html`, mock-up A): an Export section (what / when / format, checklist behind "Choose…", CSV settings with a preview table, recap before saving) and an Import section (receipt from a dry run, options per format, Open / Cancel), visually distinct, then the files of the session (show its period, remove its data, save again). Files dropped on the page (and picked from the dashboard list) go to it through `ctx.droppedFiles`. When a file holds data and dashboards, the receipt has a checkbox for each (import options `data: false` / `dashboards: false`). `File` objects must be `markRaw` (a proxied File cannot be read). Helpers tested in `webapp/tests/export.test.js`.

## Webapp notes

- Fields bound to application state use the `v-value` directive (`main.js`) with `@change`, never `:value`: panels redraw several times per second (timers, live data) and `:value` writes the stored value back over what is being typed. This bug came back three times (data menu, Edit panel names, view options) before the directive existed. When adding a text or number input, type in it in a browser while data flows before calling it done.

- Never let a UI framework proxy sample storage: `Telemetry.data` is `markRaw` (see doc/performance.md). Regression test in `tests/datastore.test.js`. Same for the caches built from it: `ViewChart.decimators` is `markRaw` (a proxied decimator compares its raw source with a proxy, never matches, and rescans all the data on every update: found on 2026-10-10 by a long session in the webapp, the lib test pages are not reactive and do not show it). When measuring performance, measure in the webapp too.
- `TP.dashboards.enableAutoDashboard(name, onCreated)` (lib, `150-dashboards.js`) charts new telemetries automatically (number -> chart, a number with both ends of its range (`ATTR|name|min|max` before its first value) -> current value, i.e. a gauge, others -> current value, `autoplot=false` skipped); the webapp enables it as "Live" and activates it on creation.
- Data menu (popup of the pause / rate control, in `top-menu.js`): data window (default 300 s) with a timeline of how much of it is filled (`TP.datastore.getTimeSpan()`: the telemetry that goes the furthest back), memory ring and stacked bar, policy at the limit, heaviest telemetries, clearing (data, and dashboards: "Empty this dashboard" = `TP.dashboards.clearDashboard(name)`, "Delete all dashboards"). The lib does the work (`TP.state.dataTimeout`, `memoryLimit`, `memoryPolicy`, `TP.datastore.getMemoryUsage/getTimeSpan/checkMemory/clearData/forgetTelemetries`).
- Top menu: `webapp/components/top-menu.js` (floating island: dashboard switcher, pause/resume + rate, left panels as one segmented control with counts, Edit, Help as a word at the right end; shortcuts Space/T/S/H/E (shown in tooltips), fades out when the mouse rests), see `doc/top-menu.md`.
